# Team Tracking Dashboard

A daily-use HR tool for a small team (4–10 people) with two manager accounts. Log positive and negative events against team members, watch a weighted score with time decay drive a five-tier status automatically, see month-over-month trends, and generate Claude-written monthly reports.

Built to reflect real HR practice — behavioural events not personality, transparent scoring not a black box, recent behaviour weighted higher, and an audit-friendly paper trail.

## Quick start

```bash
# 1. install dependencies (one time)
npm install

# 2. configure environment
cp .env.example .env
# generate a strong session password:
node -e "console.log(require('crypto').randomBytes(32).toString('hex'))"
# paste it into .env as SESSION_PASSWORD
# (optional) add ANTHROPIC_API_KEY to enable AI-written monthly summaries

# 3. create the database and seed example data
npm run db:migrate
npm run db:seed

# 4. run it
npm run dev
# visit http://localhost:3000
```

Default seeded accounts (change passwords immediately — see below):

| Role      | Email                 | Password           |
| --------- | --------------------- | ------------------ |
| Primary   | founder@example.com   | `change-me-please` |
| Secondary | manager@example.com   | `change-me-please` |

The seed data populates three example team members across all five status tiers, with ~35 events spread over the last ~110 days, plus three months of backfilled monthly snapshots so trend lines render immediately.

## Storage

SQLite, single file at `data/app.db`, accessed via `better-sqlite3` and Drizzle ORM.

**Why SQLite for this?** This dashboard is run locally by one or two managers tracking up to ten team members. Lifetime data volume is in the thousands of rows. SQLite gives:

- One process, one file. Backup is `cp data/app.db data/backup-YYYY-MM-DD.db`. Restore is the reverse.
- No separate database server to keep alive, no auth/network/version drift.
- Synchronous driver — no connection pool, no async config to misconfigure.
- WAL mode is enabled so reads don't block writes.

If the team ever needs multi-machine concurrent access, swap the Drizzle dialect to `drizzle-orm/postgres-js` with a hosted Postgres (Neon, Supabase). The schema, scoring engine, and routes are dialect-agnostic.

## How scoring works

All weights live in [`lib/scoring/config.ts`](lib/scoring/config.ts). Tune them there — no other change needed.

**Base points** by sentiment × severity:

|          | Minor | Moderate | Significant |
| -------- | ----- | -------- | ----------- |
| Positive | +2    | +5       | +10         |
| Negative | −2    | −5       | −10         |

**Time decay**: each event's contribution halves every 30 days. An event from today contributes 100%, one from 30 days ago contributes 50%, one from 90 days ago about 12.5%. Recent behaviour matters more than something from three months ago, but old patterns aren't erased.

**Score** = Σ over all of a member's events of `basePoints × decayWeight`.

**Status** is a pure function of score:

| Score      | Status            | Colour    |
| ---------- | ----------------- | --------- |
| ≥ 30       | Going great       | green     |
| 10 – 30    | On track          | teal      |
| −5 – 10    | Needs attention   | amber     |
| −20 – −5   | Behind target     | light red |
| < −20      | At risk           | red       |

Status is **never** settable manually. It always derives from the data, so the paper trail is consistent with the score.

## Monthly reports

Reports → "Generate snapshots" computes and stores an immutable monthly snapshot for every active team member: score, status, category breakdown, positive/negative event counts, and a written summary paragraph.

If `ANTHROPIC_API_KEY` is set, the summary is generated by Claude Haiku — it sees structured event data and writes a 2–4 sentence manager-style note. Without a key, the system falls back to a deterministic templated summary so the report still saves and renders.

Snapshots are idempotent: re-running the same month overwrites in place (useful after backdating events). Past months are not silently rewritten when new events land — the snapshot freezes that month's view at generation time.

## Backups

```bash
# back up before any risky operation
cp data/app.db data/backup-$(date +%Y-%m-%d).db

# restore
cp data/backup-2026-04-30.db data/app.db
```

## Changing or adding manager passwords

Two ways:

**Option 1 — change a seeded password.** From the project root:

```bash
node -e "
const Database = require('better-sqlite3');
const bcrypt = require('bcryptjs');
const db = new Database('data/app.db');
const hash = bcrypt.hashSync('YOUR-NEW-PASSWORD', 10);
db.prepare('UPDATE users SET password_hash = ? WHERE email = ?').run(hash, 'founder@example.com');
console.log('updated.');
"
```

**Option 2 — add a third manager (no UI for this since the spec is two managers, kept manual on purpose).** Same script, but `INSERT INTO users (email, password_hash, name, role) VALUES (...)`. Use `'primary'` or `'secondary'` for the role.

## Manager roles

- **Primary** can: log events, view all data, generate snapshots, **add and archive team members**.
- **Secondary** can: log events, view all data, generate snapshots. Cannot manage the team.

The "Manage" tab is hidden for secondary managers, and the API enforces the same rule (the UI is not the gate).

## Architecture (one screen)

```
Next.js 15 App Router
  ├── app/login              public
  ├── app/dashboard          team grid, profile, reports, manage
  ├── app/api                events, members, notes, snapshots, auth
  └── middleware.ts          redirects unauthenticated → /login

lib/db/                      Drizzle schema + SQLite client + migrations SQL
lib/scoring/                 weights/thresholds + the score/status/category engine
lib/reports/                 monthly snapshot generator + Claude summary call
lib/auth/                    iron-session helpers, role guards
lib/data/                    server-side query helpers used by pages
components/                  shadcn-style UI primitives + domain components
data/app.db                  the database
```

The scoring engine is **pure** — no DB access, no I/O. Everything is computed from a list of events. That makes it easy to reason about and trivial to unit-test if you want to add tests later.

## Daily flow

1. Open the dashboard. Each card shows a member, their status, score, trend, and events this month.
2. Spotted something? Click the **Log event** button on the card. Pick category, sentiment, severity, write a short note. Save.
3. End of month: go to **Reports** → **Generate snapshots**. The system writes a paragraph for each member. Read, share, file.
4. Need a hard conversation? Open the member's profile, hit the relevant monthly report, print or screenshot. The trail is timestamped, behaviour-based, and signed by which manager logged each event.

## Resetting

```bash
npm run db:reset    # wipes data and re-seeds
```
